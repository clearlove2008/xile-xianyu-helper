# 售罄商品自动重新上架（自动补货）

> 商品卖完一件后闲鱼会把它挪到「已售出」分组并从在售列表消失。这个功能按固定周期巡检该分组，
> 把仍然该卖的商品重新挂回在售，并顺带补上库存，避免「卖完就断货」。

## 1. 工作原理

闲鱼没有独立的「上架」接口，PC 编辑页的链路是：

```
mtop.idle.pc.idleitem.editDetail  →  取回商品可编辑数据
mtop.idle.pc.idleitem.edit        →  原样回填一次（带 itemId 即重发布）
```

自动补货复用同一条链路：

1. 每 N 分钟（默认 2 分钟）读一次账号的商品分组（`mtop.idle.web.xyh.item.list`，`needGroupInfo=true`）。
2. 只挑「已售出 / 售罄」分组；「已下架」默认不碰，避免把人工下架的商品又挂回去。
3. 对分组里的每个商品：
   - 若本地订单表里还有未完成订单（未发货 / 未完结），跳过，防止同一件商品被卖两次；
   - 否则调 `editDetail → edit` 重新上架，库存按配置数量提交。
4. 失败退避 30 分钟，成功 1 分钟后才允许再次处理同一商品；单轮最多处理 5 件。

## 2. 配置

配置存在系统设置表（`system_settings`），**保存后下一轮巡检即生效，不需要重启**。

| 键 | 默认值 | 说明 |
|---|---|---|
| `reshelf_enabled` | `true` | 总开关，`false`/`0`/`off` 关闭 |
| `reshelf_interval_minutes` | `2` | 巡检周期（分钟） |
| `reshelf_quantity` | `5` | 重新上架时提交的库存件数 |
| `reshelf_max_per_scan` | `5` | 单轮最多重新上架的商品数 |
| `reshelf_include_offline` | `false` | 是否连「已下架」分组一起上架 |

关闭自动补货（立即止血）：

```sql
INSERT INTO system_settings (key, value) VALUES ('reshelf_enabled','false')
ON CONFLICT(key) DO UPDATE SET value = 'false';
```

## 3. 观测

每轮巡检都会写一条日志到 `logs/server.log`：

```
msg="重新上架巡检完成" accounts=1 reshelf=0 outcomes=0 elapsed=1.2s
```

有商品被处理时会另有明细：

```
msg="已重新上架" account=1654458395 item=1100507197559 title=... quantity=5
msg="重新上架失败" account=... item=... err=FAIL_BIZ_...
```

## 4. 已知边界

- 只扫描启用了、并且本地有商品记录的账号，避免对空账号空跑接口。
- 需要账号凭证有效；凭证失效时本轮跳过并记录日志，等续期系统恢复。
- 有未完成订单时不会上架；订单完结后下一轮才补货。
- 库存会按配置值**重置**（不是累加），因此把 `reshelf_quantity` 调小会减少在售库存。

## 多库存发布策略（2026-11-17 补充，同日修正）

平台对多库存的限制是**账号级**的，发布与编辑接口共用同一错误码
`FAIL_BIZ_ITEM_ERROR_MULTI_INVENTORY_ITEM_CAN_NOT_PUBLISH::亲，您不能发布多库存宝贝哦`：

| 账号 | 新建商品填 5 件（publish） | 编辑已有商品改 5 件（edit） |
|---|---|---|
| 喜乐程序员 (1654458395) | 拒绝 | 允许（实测 `itemStatus` 由 -1 转 0，库存生效） |
| 喜乐API (2222518039340) | 拒绝 | **同样拒绝**（2026-11-17 12:28 实测，item 1101934444200） |

因此发布链路是「先发 1 件、再尝试补库存」，实现见 `internal/xianyu/mtop/publish.go` 的 `publishStockPlan`：

1. 单规格商品且用户填写的库存 > 1 时，发布请求按 1 件提交；
2. 发布成功拿到 `item_id` 后，调用 `ReshelfItem` 把库存补到目标值；
3. 补库存失败间隔 2 秒重试一次；命中多库存拒绝属确定性错误，不重试，商品保持 1 件
   并在响应里返回 `stock_warning`（提示该账号被平台限制多库存）；
4. 多规格商品的库存由 SKU 汇总，不走这条降级路径。

巡检侧同理：`internal/relister` 售罄补货遇多库存拒绝会按 1 件降级上架，并在进程内记住
该账号（`multiInventoryDenied`），后续直接按 1 件提交。如需恢复多库存，请在闲鱼侧
确认该账号的多库存/鱼小店权限后重启服务（进程内记忆会重置）。

相关错误码：`multi_inventory_not_allowed`（HTTP 403），与 `stock_permission_missing` 区分——前者是平台限制该账号多件库存，后者是账号缺库存权限。

## 无分组账号的兜底巡检（2026-11-17 补充）

部分账号（实测喜乐API）的平台侧差异会导致常规巡检失效：

- `item.list` 不返回 `itemGroupList` → `FetchItemGroups` 恒为空，分组巡检跳过该账号；
- 订单同步 `mtop.taobao.idle.trade.merchant.sold.get` 返回 `PERMISSION_EXCEPTION`，订单表无数据；
- `item.list` 的 `pageSize` 超过单页上限会直接 `FAIL_BIZ_FORBIDDEN`（需用 20）。

处理方式（`internal/relister/relister.go` 的 `scanGrouplessAccount`）：

1. 账号候选集不再按 `item_info.deleted_at` 过滤（商品卖完被全量同步软删后，账号不能退出巡检）；
2. 无分组账号的候选 = 本地 `item_info` 行（含软删，最多 50 条）减去当前在售列表（最多 3 页 × 20 条）；
3. 逐个读取 `editDetail`，库存为 0（售罄）才重新上架；仍有库存（人工下架）不动，
   保持「已下架分组默认不自动上架」的语义。

## 默认发货地（2026-11-17 补充）

无显式发货地的发布（AI 出图等入口）可能被平台拒绝：
`FAIL_BIZ_ITEM_EDIT_INVALID_MAP_LOCATION::系统无法定位您所在的行政区`（平台对多数账号能用资料兜底，个别账号兜不出来）。

处理方式：

1. 系统设置 `default_publish_location` 存一份默认发货地 JSON（当前取自本账号真实在售商品：
   云南 昆明 官渡区，divisionId 530111，gps 24.950285,102.748888）。
2. 发布请求未带 `location` 表单字段时，服务端自动回退到该默认值（`internal/server/item_handlers.go` 的 `defaultPublishLocation`）。
3. `poiId`/`poiName` 为空时不再提交空字段，与平台 editDetail 返回的 `itemAddrDTO` 结构一致。
4. 该错误单独归类为 `invalid_map_location`（HTTP 403），前端提示检查默认发货地。

改默认发货地：更新 `system_settings` 的 `default_publish_location` 为
`{"area":"区","city":"市","division_id":"adcode","latitude":lat,"longitude":lng,"poi_id":"","poi_name":"","province":"省"}`，改完即生效，无需重启。
